# Story 6.1: 多重物理与逻辑租户隔离的硬管控边界

Status: done

## Story

As a 系统根管理组,
I want 在顶层能够一键开辟出归属给例如分部公司A、子公司B的专属带容量配额及空间隔离的云环境,
so that 使得母公司下所有的子机构互不侵犯不泄漏并享受集团统管.

## Acceptance Criteria

1. **AC1 - EE 版本守卫**：所有 Workspace 管理 API（创建/删除/重命名/列表）仅限 EE 版本可用。CE/PE 版本调用返回 HTTP 403 + 版本不支持提示。`GET /workspace/by_user` 与 `GET /workspace/current_user` 不受版本限制（供前端下拉使用）。

2. **AC2 - Workspace CRUD（超级管理员）**：
   - `GET /workspace` → 返回全部 Workspace 列表（仅 ADMIN 角色可见）
   - `POST /workspace` → 新建 Workspace（字段：`name` 必填，最长 64 字符；唯一性校验）
   - `PUT /workspace/{workspace_id}` → 重命名 Workspace（唯一性校验）
   - `DELETE /workspace/{workspace_id}` → 删除 Workspace（若空间下存在知识库或应用资源，拒绝删除并返回提示）
   - `GET /workspace/by_user` → 返回当前登录用户所属 Workspace 列表（用于首页切换下拉）
   - `GET /workspace/current_user` → 返回当前用户可操作的 Workspace 列表（用于添加成员弹窗）

3. **AC3 - Workspace 成员管理**：
   - `GET /workspace/{workspace_id}/user_list/{current_page}/{page_size}` → 分页获取成员列表（支持 `username`/`nick_name` 过滤）
   - `GET /workspace/{workspace_id}/user_list` → 获取全部成员（不分页，供授权选择器使用）
   - `GET /workspace/{workspace_id}/user_member` → 获取成员详情（含角色信息）
   - `POST /workspace/{workspace_id}/add_member` → 批量添加成员（`[{user_id, role_id}]`），已存在成员幂等处理
   - `POST /workspace/{workspace_id}/remove_member/{user_relation_id}` → 移除成员（删除 `WorkspaceUserRoleMapping` 记录）

4. **AC4 - 数据隔离（Zero-Trust 围墙）**：Workspace 下所有资源（知识库、应用、工具、模型）的查询必须附带 `workspace_id` 过滤条件。后端绝不信任前端传入的 `workspace_id`，必须从 Token 解析出的用户-工作空间映射中强校验。越权读写的请求必须被 `@has_permissions` 中间件拦截，返回 403。

5. **AC5 - 默认 Workspace 向下兼容**：所有历史资源（`workspace_id="default"` 的记录）在 EE 升级后归属到系统默认 Workspace，不丢失数据。`GET /workspace/by_user` 对 CE/PE 版本直接返回含 `default` workspace 的单条记录，保证前端正常工作。

6. **AC6 - WorkspaceUserRoleMapping 模型注册**：`workspace_model` 与 `workspace_user_role_mapping` 必须通过 `DatabaseModelManage` 在 EE 模式下完成注册，CE 模式 `DatabaseModelManage.get_model("workspace_model")` 返回 `None`，相关功能优雅降级。

7. **AC7 - 前端已完整实现（禁止修改）**：前端工作空间管理页 `ui/src/views/system/workspace/` 及相关 API 封装 `ui/src/api/workspace/workspace.ts` 均已就绪，后端只需精确匹配 API 契约。

### 🔥 核心架构发现：EE 模型注入模式

**关键机制：`DatabaseModelManage` 动态注入**

```python
# apps/common/database_model_manage/database_model_manage.py
class DatabaseModelManage:
    model_dict = {}

    @staticmethod
    def get_model(model_name):
        return DatabaseModelManage.model_dict.get(model_name)

    @staticmethod
    def init():
        for h in handlers:
            model_dict = h.get_model_dict()
            DatabaseModelManage.model_dict = {**DatabaseModelManage.model_dict, **model_dict}
```

EE 模块通过自定义 handler 向 `model_dict` 注入模型，CE 版不注册，`get_model()` 返回 `None`。
开发者必须在序列化器中对 `None` 优雅降级，而不能假设模型一定存在。

**CE 降级模式（必须遵守）：**

```python
workspace_model = DatabaseModelManage.get_model("workspace_model")
if workspace_model is None:
    # CE/PE 版本：返回默认 workspace
    return [{"id": "default", "name": "Default Workspace"}]
# EE 版本：正常查询
return list(workspace_model.objects.all().values('id', 'name', 'create_time'))
```

```python
class WorkspaceUserRoleMapping(AppModelMixin):

        db_table = "workspace_user_role_mapping"
        unique_together = ('workspace', 'user')
```

### 🚫 删除保护逻辑

```python
def delete_workspace(workspace_id):
    from knowledge.models import Knowledge
    from application.models import Application

    knowledge_count = Knowledge.objects.filter(workspace_id=workspace_id).count()
    application_count = Application.objects.filter(workspace_id=workspace_id).count()
```

### 💡 陷阱与防护

1. **`workspace_id` 是 CharField 非 FK**：所有资源表的 `workspace_id` 是 `CharField(default="default")`，不是外键，因此删除 Workspace 不会自动级联删除资源。须在应用层做前置检查（见删除保护逻辑）。

2. **Default Workspace 不可删除**：`id="default"` 的 Workspace 是系统保留记录，必须在 `delete_workspace` 中硬判断拒绝删除。

3. **CE 版 `by_user` 接口不得 500**：前端在 CE 版也会调用 `GET /workspace/by_user`，必须优雅返回 `[{id: "default", name: "Default Workspace"}]` 而非报错。

4. **`role` 字段存储方式**：`WorkspaceUserRoleMapping.role` 存储 `RoleConstants` 枚举值字符串（如 `"WORKSPACE_MANAGE"`），与 `permission_constants.py` 的 `RoleConstants.WORKSPACE_MANAGE.value.id` 对应，Token 解析时用于构造 Permission 路径。

5. **`GET /workspace/{id}/user_list` vs `GET /workspace/{id}/user_list/{page}/{size}`**：两个路由的 URL 会有前缀冲突，务必在 `urls.py` 中把 `/user_list/<int:current_page>/<int:page_size>` 放在 `/user_list` 之前匹配，或用不同路径名区分。

6. **并发唯一性约束**：`WorkspaceUserRoleMapping` 的 `unique_together=('workspace','user')` 在高并发 `add_member` 时可能触发数据库唯一约束异常，使用 `update_or_create` + `IntegrityError` 捕获处理。

7. **Token 刷新**：用户被移出 Workspace 后，其现有 Token 中的 workspace 权限声明并未立即失效。Token 的 workspace 权限需在每次请求时从数据库实时验证（`is_workspace_manage()` 函数已有此逻辑），不可依赖 Token 缓存。
